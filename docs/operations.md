# Operations

## Local setup

Use a Python virtual environment and install the package in editable mode. OpenSSH client and `ssh-keygen` are required for remote execution. No root access is required to install or run RunbookOS. The default state DB is `state/runbookos.sqlite3` in a source checkout or `~/.local/state/runbookos/runbookos.sqlite3` in a normal install. AI inference is optional and uses the configured HTTP provider only when `investigate` is invoked. The separately configured `tunnel` command runs in the foreground and exits when interrupted.

Inspect `runbookos --help`. Validate a runbook first; create a plan and review every target/action/argument and policy decision before executing. `check` is read-only-only. Remediation uses the explicit sequence: plan → operator review → approve with reason → run. An approval is valid once and expires according to policy.

## State lifecycle

- Plans remain in SQLite for audit and can be re-run only when unchanged; approval for mutations is one-time.
- Executions use `running`, `succeeded`, `failed`, or `unknown`. An unclean controller exit can leave `running`; treat it as interrupted/uncertain and inspect the target before any new plan.
- SSH `unknown` means dispatch may have reached the host. Inspect `runbookos history EXECUTION_UUID`, target service state, and logs manually. Do not replay a mutating step just because SSH timed out.
- Run `runbookos audit` to verify the local event chain. Back up the DB with restrictive permissions and send an independent copy to trusted storage for recovery.
- `runbookos investigate --incident-stdin` reads bounded incident text from stdin, selects from the configured diagnostic catalog, executes only policy-allowed read-only diagnostics, and stores a validated Minimal Semantic Reply v2 assessment. Review linked evidence and assertion/verification states through `runbookos history EXECUTION_UUID` and the incident assessment projection. Model classifications remain suspected, confidence is uncalibrated, and citations do not prove semantic support. Provider or contract failures are persisted as sanitized failed investigations; they are not abstentions or diagnoses. Assessment text is advisory and cannot approve or execute a plan.
- `runbookos investigations` lists investigation metadata and evidence references without echoing incident text. Additive migrations have advanced SQLite to `user_version=4` while retaining prior plan, approval, execution, investigation, incident, and audit data. Downgrade is unsupported.
- SQLite schema version is currently v4. Use `runbookos state backup` for a consistent backup while WAL mode is active; never copy only the main database file. Verify the new copy before considering recovery.
- Read-only `systemd.journal_tail` is available only when explicitly allowed by the target policy. It accepts a registered unit and at most 50 lines, enforces a 10-second maximum timeout and a 64 KiB remote-output cap, and redacts common credential patterns. Logs remain sensitive and redaction is not exhaustive; keep the action default-deny unless the data handling is approved.
- Server/OS diagnostics are registered, read-only actions and remain default-deny per target. Add only reviewed action IDs to that host's `diagnostic_actions`; units passed to service and journal tools must also appear in `allowed_units`. The example policy is opt-in guidance, not a policy automatically applied to installed hosts.
- `os.cpu` reports Linux load averages and cumulative `/proc/stat` tick counters; it does not derive utilization percentages from a single sample. `os.release` reports selected `/etc/os-release` identity fields plus kernel and architecture metadata; it never evaluates the file as shell code. `process.list`, `process.inspect`, and `process.tree` report bounded PID/name/state/UID/CPU-tick/RSS metadata and never collect command lines, arguments, or environment. List/tree limits are schema-bounded; PID inspection is only for an explicitly supplied numeric PID.
- `filesystem.mounts` reports mountpoint, filesystem type, and read-only state, omitting device/source strings. It examines at most 128 records. Legacy `os.disk` and `filesystem.inodes` require each explicit path in the host's `allowed_storage_paths` policy list; an action allow alone does not authorize arbitrary paths. The pathless `os.disk` form retains its fixed `/` default. `filesystem.inodes` runs a fixed `stat` invocation against one explicit absolute normalized path, with a 3-second action timeout; inaccessible or unsupported filesystems return an explicit failed observation rather than a healthy result. Mount and path names can reveal host layout and should be treated as operational metadata.
- Scoped storage diagnostics require an inventory `storage_targets` alias and a matching per-host `allowed_storage_targets` policy entry. `filesystem.pressure` uses file-descriptor-based filesystem statistics to distinguish byte exhaustion, inode exhaustion and both together, including read-only state and unknown capacities. `filesystem.mount_status` checks one expected mountpoint against bounded mount inventory; a missing mount is asserted only when that inventory is complete. `filesystem.path_metadata` reports type, permissions, size and modification time without reading contents or following symlinks. `filesystem.usage_summary` counts regular-file bytes below one registered directory, with a five-second/1024-entry ceiling, hardlink deduplication, no symlink following, and no descent into known mountpoints or different devices; incomplete scans are unknown. `filesystem.log_growth` records two file metadata snapshots and an observed interval; it reports unknown on replacement or missing files. The example `storage-filesystem-review.yml` remains denied until a private inventory and policy explicitly register its aliases. These observations are hypotheses and do not establish a verified root cause.

### Application and web review

Configure a private `applications` profile on the exact host, then allow its ID in `allowed_applications` and separately allow every referenced probe and storage alias. The example profile is commented out and the example policy lists no allowed application IDs. `application-web-review.yml` validates offline but is denied at planning until the operator registers its sources. A worker step uses the existing `systemd.service_status` and `allowed_units`; dependency steps use existing `network.tcp_connect`, `network.listener`, `network.tls_certificate` or `filesystem.pressure` as appropriate. The profile binds the observations for correlation; it does not authorize any of those steps on its own.

| Action | Input and source | Limit | Evidence status and failure | Confidence and limitation |
| --- | --- | --- | --- | --- |
| `application.health` | `application_id`; pinned HTTP(S) health endpoint | 10 s; one GET; no redirect follow or body read | HTTP status, duration, redirect category, safe content-type category; `healthy`, `unhealthy`, `redirect`, `unknown` | A 2xx response is endpoint readiness, not verified application correctness. TLS trust and hostname are enforced. |
| `application.queue_health` | `application_id`; pinned HTTP(S) queue endpoint with numeric `X-Queue-Depth` and `X-Queue-Oldest-Age-Seconds` headers | 10 s; one GET; depth ≤1,000,000 and age ≤86,400 s | `healthy`, `backlog`, `unhealthy`, `unknown`; missing/invalid metrics are unknown | Reports only operator-pinned thresholds; never reads messages or payloads. |
| `application.config_fingerprint` | `application_id`; registered non-secret file and pinned SHA-256 | 3 s; regular single-link file ≤64 KiB; no-follow open | `matched`, `drift`, `unknown`; hash only, no contents | A mismatch is an observation, not proof of causal failure. |
| `application.deploy_version` | `application_id`; registered safe version file and pinned expected version | 3 s; regular single-link file ≤64 bytes; no-follow open | `matched`, `drift`, `unknown`; strict version token only | Does not invoke deployment tools or prove rollout health. |

An application profile may reference at most eight dependency endpoint aliases and eight explicitly related directory storage IDs. The execution summary reports each dependency as `healthy`, `unhealthy`, `missing`, or `unknown` using persisted TCP evidence. A timeout is `unknown`; a closed/refused connection is unhealthy. It also links observed HTTP 502/503, unavailable local listeners, stopped worker, queue backlog, configuration/version drift, TLS invalidity and storage pressure to step IDs. `resource_pressure` is application-specific only when the pressure observation's `storage_id` matches a profile `pressure_storage_ids` entry that is also authorized by the host policy. Other pressure observations remain labeled `host_context`, with their step ID and storage ID (if available); missing or incomplete pressure remains unknown. Signals are observations and `verified_root_cause` remains false. This review does not parse proxy configuration, queue payloads, application secrets, or unrestricted logs.

An execution or step status of `succeeded` means the diagnostic measurement ran successfully. It does **not** mean the application is healthy: an HTTP 503 without assertions leaves execution `succeeded`, while the persisted step evidence and `application_correlation.health` report `unhealthy` with status 503. The CLI history exposes execution evidence, and the authenticated incident dashboard displays recorded observation results separately from execution status. Operators must inspect the observed health status before treating a check as healthy.
- `process.list` sorts by RSS descending with PID as a stable tie-break when `order_by: memory_rss`, then returns the first `limit` entries; PID ordering remains ascending. `truncated` flags either a limited result or incomplete scan, `scan_truncated` identifies scan limits/timeouts, and `inventory_complete` is false if entries were omitted or unavailable. `process.tree` reports the same completeness fields, so a partial tree is not represented as a complete inventory. `process.inspect` is a single-PID lookup and fails if that PID cannot be read.
- `systemd.service_status` reads a fixed set of `systemctl show` properties for one policy-allowed `.service`. `systemd.failed_units` is capped at 100 units and 16 KiB of command output. `systemd.journal_summary` summarizes priority counts and timestamps for at most 200 records from a bounded time window and never returns log messages. `systemd.timers` returns at most 100 timer/activation pairs and a schedule summary; its source output is capped at 32 KiB.
- `os.packages` returns at most 100 sorted installed package names and versions from the detected dpkg or RPM database; subprocess output is capped at 256 KiB and runtime is bounded by the runbook's action timeout (maximum 10 seconds). `os.cron` inspects only `/etc/crontab`, regular non-symlink files under `/etc/cron.d`, and periodic directory entry counts. It reports schedule fields and source names but deliberately omits users and command bodies. File reads and entries are capped. These tools do not inspect per-user crontabs or execute scheduled jobs.
- These observations are point-in-time snapshots. Process exit, concurrent mounts, systemd state changes, package database updates, and journal rotation can make later observations differ. Missing permissions, unavailable utilities, malformed data, and output/time limits remain failed/unknown evidence; they are not inferred as healthy. The action result, target, step ID, execution timestamps, and assertion results continue through the existing execution/evidence/audit store. No Server/OS tool adds a mutating action or changes approval semantics.
- `examples/runbooks/server-os-inspection.yml` demonstrates the bounded diagnostics as a read-only review. `examples/runbooks/server-os-process-tree.yml` uses sample PID 1 and a process-tree cap; replace the numeric PID in the runbook before planning a different inspection. Their target names and action permissions are examples; operators must register their own inventory and explicitly authorize each diagnostic action in policy.
- `network.resolver_config` reads at most 4 KiB from `/etc/resolv.conf` and reports configured nameservers/search domains. It does not perform a DNS query and does not establish that resolution works. It also remains subject to the normal per-host default-deny policy.
- Network/DNS/TLS review uses registered `network.dns_resolve` (5 seconds, one A query, 2 KiB reply), `network.listener` (3 seconds, at most 4096 IPv4 TCP entries), and `network.tls_certificate` (10 seconds, one pinned private IPv4 TLS connection). Each requires a strict `endpoint_id` argument, inventory endpoint definition and explicit `allowed_probe_targets` entry. DNS endpoints also require fixed `dns_name` and private `resolver_address`; TLS requires HTTPS and `dns_name`. `network.listener` is a separate local-host observation: planning requires `local_listener: true` on the endpoint, and remote dispatch checks the configured private IPv4 address against the observed SSH host's bounded local IPv4 address inventory before reading `/proc/net/tcp`. A different-host address yields uncertain `not_applicable`; unavailable or truncated address inventory yields uncertain `unknown`. Neither is evidence that the remote service port is closed. `network.firewall_summary` (5 seconds, 64 KiB source cap) is separately default-deny and returns only nftables table/chain/rule counts when the existing account can read them.
- Existing `network.interfaces` and `network.routes` retain their JSON list evidence fields, now with a fixed 15-second maximum action timeout and 64 KiB source-output cap. Missing utilities, oversized output and malformed JSON return uncertain failed observations.
- Read `data.status` for DNS (`matched`, `mismatch`, `nxdomain`, `no_a_record`, `resolver_failure`, `resolver_unavailable`, `timeout`, `invalid_response`), listener (`listening`, `address_mismatch`, `port_closed`, `not_applicable`, `unknown`), and `data.certificate_status` for TLS (`valid`, `expired`, `hostname_mismatch`, `invalid_chain`, `invalid_certificate`, `timeout`, `unavailable`). A partial listener scan is an uncertain failed observation. DNS/TLS timeout and unavailable states remain `unknown` in engine execution even when dispatch returns `ok: true`; assertions are not evaluated for uncertain records. DNS mismatch, local closed listener, outbound TCP timeout, route output and TLS failure can coexist; compare their separate step IDs, timestamps and audit records. This is correlation evidence, not a verified causal conclusion. A route mismatch requires inspection of the existing `network.routes` observation and independent operator interpretation. The example runbook stays denied until an endpoint is registered in private inventory.
- Provider timeouts, invalid JSON, unknown diagnostic IDs, unsupported evidence references, or policy denial stop the investigation. No tool call is retried and no recommendation is executed.
- For local host inference from a VM, use a dedicated tunnel identity and pinned host key. Start `runbookos tunnel config/tunnel.yml` in a supervised terminal, then run `investigate` in another shell with `RUNBOOKOS_LLAMA_API_KEY` present. Do not put the API key in command arguments or shell history. Stop the tunnel with Ctrl-C after the investigation. No service persistence is configured by RunbookOS.

## Approval and access

The local OS username is recorded as the approval actor. The operator must state a useful change/incident reason. The approval stores the plan hash, expires in 900 seconds by default, and is consumed atomically before dispatch. A policy denial cannot be overridden by approval. Do not grant remediation in policy until the target OS permissions and recovery procedure are reviewed. No action invokes sudo.

## Recovery

If the controller process stops, inspect SQLite history. If a row remains `running`, classify the result as uncertain; RunbookOS does not resume or retry an in-flight plan or investigation. Restore the SQLite DB from a protected backup if damaged, then run `audit`; do not edit chain rows to make verification pass. A lost DB also loses local plan/approval/investigation state, so re-plan and obtain fresh approval.

### PostgreSQL database diagnostics

`postgresql.protocol_available` remains a one-byte protocol probe. It does not authenticate. The new `postgresql.inspect` action accepts only `{endpoint_id, check}` with `check` one of `readiness`, `connections`, `replication`, or `sessions`. Each action is read-only, has a 10-second maximum, fixed SQL, one JSON aggregate row, and a 4 KiB response limit. Inventory must bind a private IPv4 address, TLS hostname, database, read-only user, and credential alias; policy must separately allow the action and endpoint. The remote user needs a 0700 `~/.config/runbookos/pgpass` directory and 0600 credential file named by the alias. Provision these outside the repository. libpq uses `verify-full`, a read-only transaction default, 5-second statement timeout, and 1-second lock timeout. SQL statistics require `pg_read_all_stats`; without it, aggregates are unknown. No application rows, query text, client addresses, or session identities are returned. `postgresql.start_fixture` remains disposable-only.

| Action | Source | Evidence | Unknown or failure |
| --- | --- | --- | --- |
| `postgresql.protocol_available` | Pinned endpoint SSL negotiation | `protocol_available`, `ssl_supported`; no authentication | TCP or protocol failure |
| `postgresql.inspect` `readiness` | Fixed `pg_is_in_recovery()` SQL | Authenticated query success and role flag | Credential, TLS, authentication, query failure |
| `postgresql.inspect` `connections` | `pg_stat_activity`, fixed settings | Active/idle/total, maximum and reserved capacity, utilization, possible exhaustion | Missing stats privilege, malformed response, timeout |
| `postgresql.inspect` `replication` | `pg_stat_replication`, `pg_stat_wal_receiver` | Primary/standby and observed peer counts/lag | Missing privilege or peer evidence; standalone is not failed replication |
| `postgresql.inspect` `sessions` | Aggregate `pg_stat_activity` | State counts, long transactions and queries, waits, oldest age | Missing privilege or statistics |

All checks use only inventory aliases and per-host default-deny policy. Diagnostic execution success means the observation was captured; it does not mean the database is healthy. Database correlation remains endpoint-scoped with step references and `verified_root_cause: false`. Run the read-only [example](../examples/runbooks/database-data-review.yml) only after configuring a trusted private source and policy. RunbookOS SQLite `state backup` below concerns controller state, **not** PostgreSQL application-database backups; those remain outside this R1 package.

### Schema-v4 backup, verification, and staging restore rehearsal

Use an existing directory owned by the current user with mode 0700 and a destination filename that does not exist. The source database and its parent must also be private and owned by the current user. These commands work offline and do not require inventory, SSH, or a provider:

```sh
umask 077
install -d -m 700 "$BACKUP_DIR"
runbookos --db "$DB_PATH" state backup --output "$BACKUP_DIR/runbookos.sqlite3"
runbookos state verify-backup "$BACKUP_DIR/runbookos.sqlite3"
runbookos state rehearse-restore "$BACKUP_DIR/runbookos.sqlite3" --output "$BACKUP_DIR/staging.sqlite3"
runbookos state validation-status "$BACKUP_DIR/runbookos.sqlite3" --staging "$BACKUP_DIR/staging.sqlite3"
runbookos state review-staging "$BACKUP_DIR/staging.sqlite3"
```

Both commands print only JSON `status` (`PASS`, `FAIL`, or `UNKNOWN`) and a fixed `reason_code`; exit code 0 means PASS and 1 means failure or an unknown outcome. Successful output also gives schema version, audit event count, and `audit_empty`. An empty chain passes only for an otherwise empty state; the chain is locally tamper-evident but lacks an external trusted anchor. A valid chain does not establish causal correctness or external provenance. Backup creates a private partial file, validates the snapshot with SQLite integrity, foreign-key, schema-v4, and audit checks, then atomically publishes the new destination. It will not overwrite an existing path or follow symlinked path components. On interruption, only the command's own partial file is removed; an `UNKNOWN` result after publication may leave a complete destination that the operator must verify separately.

Keep the backup directory on a trusted filesystem with trusted ownership and restrictive permissions. The snapshot contains sensitive incident and evidence data. Encrypted and off-host storage, retention, and access control are the operator's responsibility. The source connection uses SQLite `mode=ro`; in WAL mode SQLite may still create or update auxiliary `-shm` sidecar state to coordinate readers. The main source database is not migrated or written by backup. `verify-backup` opens the snapshot immutable/read-only and does not mutate it.

`state rehearse-restore BACKUP --output NEW_STAGING_DB` first validates the input backup, copies it through SQLite's backup API to a private temporary file in the destination directory, validates schema v4, integrity, foreign keys, and the complete audit chain, then compares row counts and a logical SHA-256 over fixed tables. The hash is an equality assertion only; it is not a signature or external trust anchor. It publishes to a new path without replacing existing files and validates the staged history summary before publication. `state review-staging PATH` repeats verification and reports counts for incident, investigation, execution, and approval states through an immutable read-only connection. It does not initialize/migrate the database, consume approvals, resume uncertain executions, or dispatch work. Identifiers, event payloads, evidence, reasons, and filesystem paths are omitted from output. A `PASS` means an internally consistent offline staging copy matches the validated backup; it does not prove the backup was historically correct or that an operational disaster recovery will succeed.

Path checks reject symlinks, path traversal, aliases, non-owner files, group/world-readable files, and non-private parent directories. As with ordinary pathname APIs, checks and later opens cannot eliminate every time-of-check/time-of-use race. Run only in a trusted owner-only directory that other local users cannot modify. On a failure after publication but before directory synchronization, the command removes its own staging inode when it can verify the inode still matches; otherwise it returns `UNKNOWN` and the operator must inspect the exact output path. To discard a successful rehearsal, confirm the staging path is the dedicated new path and is not configured as an active database before removing that one file. Do not overwrite the active database or change its configured path; actual activation/restoration remains a separately reviewed and authorized operation. Schema downgrade is unsupported; package rollback does not roll back a database migration. Rehearsal does not establish the production recovery gate.

For a controller or managed-host outage, use the environment owner's independent console/recovery path. RunbookOS does not change network topology, firewall policy, or install agents as part of diagnosis. Its optional inference tunnel is foreground-only and must be stopped by its operator; RunbookOS does not create a service unit or auto-start configuration.

For synthetic incident fixtures and evaluation semantics, see [incident-evaluation.md](incident-evaluation.md). `runbookos evaluate` does not connect to managed hosts or inject faults.

`state validation-status` reuses `verify-backup` and optionally `review-staging` to show separate backup-integrity, audit-chain, and staging-review gates. It deliberately reports backup creation, rehearsal provenance, and production recovery readiness as `NOT_VERIFIED`: a valid current file does not prove how it was created, and staging review does not prove that a specific rehearsal command produced it. Keep the original operation outputs as separate evidence.

## SSH access changes

Provisioning or rolling back a managed account is an operator-approved environment change and is outside automatic RunbookOS execution. Keep exact key fingerprints and before/after metadata in the environment's protected change record. Remove only the exact authorized key entry introduced for the change; preserve administrator accounts, unrelated keys, and SSH configuration. Do not change routes, firewall policy, sshd, or services to work around reachability without separate approval.
