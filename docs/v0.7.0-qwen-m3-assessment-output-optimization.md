# RunbookOS v0.7.0 — Qwen M3 Assessment Output Optimization

**Scope: offline only. No model process or inference request was run.**

## Finding

The six-case pilot confirms a stage-two output reliability problem, but does not
prove its precise server-side cause:

- Diagnostic selection completed valid JSON/schema/catalog checks in 6/6 cases.
- Four assessment replies used exactly the 700 completion-token allowance and
  were rejected as incomplete/malformed JSON suspected. Their response finish
  reason was not available; truncation is therefore **suspected, not confirmed**.
- One assessment response was valid and was a concise 39-token abstention.
- `web-normal-01` assessment timed out at 120.105 seconds measured wall time;
  the configured provider timeout is 120 seconds. Its completion-token usage
  was unavailable.

The four capped replies took 115.325–115.938 seconds, or about 6.0 generated
tokens/second. A 700-token response leaves roughly 4.1–4.7 seconds before the
120-second request timeout. At the measured rate, even an 800-token cap would
take about 132 seconds. The evidence does not support raising the cap while
keeping the approved timeout. The timed-out normal case has no response token
count or finish reason, so the trace cannot distinguish token-generation
exhaustion from a server stall or another provider-side delay.

## Contract review

The adapter requires exactly these seven top-level keys in its model response:
`inferences`, `hypotheses`, `classifications`, `unknowns`,
`recommended_next_steps`, `overall_uncertainty`, and `assessment_status`. The
provider Pydantic model supplies defaults for several list fields, but the
adapter's strict output contract still requires every top-level key. Extra
keys are rejected.

Non-empty nested entries must satisfy the existing `ModelAssessmentReply` and
`StructuredAssessment` schemas. Inferences require a statement and at least one
evidence reference. Hypotheses require a statement and finite confidence;
reference/gap/check lists may be empty. Classifications require an allowed
category, finite confidence, and status; supporting references may be empty.
Unknowns require a question; their reference and missing-evidence lists may be
empty. Recommendations are bounded advisory strings. The adapter constructs
`StructuredAssessment.observations` from the supplied fixture evidence; the
model is explicitly told not to emit or invent observations.

The existing server profile uses a 12,288-token context, one parallel slot,
four threads, reasoning disabled, and server timeout 130 seconds. The
authenticated provider client has a 120-second timeout. The trace's prompt
usage was about 464–515 tokens for failed assessment responses, so the observed
700 completion cap—not context capacity—is the supported output-bound concern.

## Changes

The selection and assessment calls now use separate hard-bounded constants:

| Stage | Previous cap | Current cap | Rationale |
|---|---:|---:|---|
| Diagnostic selection | 700 | 700 | Preserve the proven selection behavior and budget. |
| Structured assessment | 700 | 700 | Keep within the 120-second timeout; no safe evidence supports a higher cap. |

The assessment prompt now presents the seven-key contract more compactly,
directs the model to prefer empty arrays when content is unsupported, and asks
for at most one concise justified item per non-empty array. It explicitly
keeps fixture observations adapter-owned, limits classifications to the
existing literal catalog, requires exact evidence aliases, states that fixture
evidence cannot support a `supported` classification, permits an
empty-classification abstention, and retains the advisory-only/no-command
restriction. It does not alter the parser, validator, schema, model, timeout,
or selection prompt. Malformed and truncated JSON remain rejected without
repair or conversion to abstention.

## Timeout interpretation

The `web-normal-01` trace establishes a provider timeout at the configured
120-second client boundary (120.105 seconds measured around the call). There is
no completion-token count or finish reason for that request. It is not possible
to determine from available evidence whether the model generated too long,
stalled, or encountered another provider delay. The timeout and no-retry
behavior remain unchanged.

## Offline verification

Focused M3 adapter regression tests: **51 passed**. They cover independent stage
budgets, hard-budget arguments, minimal valid abstention, full nested responses,
missing fields, nested validation errors, malformed/truncated JSON rejection,
unsupported verified claims, forged references, stage-two timeout with
selection retention, no retry, gold-label isolation, and the existing
no-executor path.

Full offline suite: **292 passed, 11 skipped** (all skips are opt-in live
AI/SSH/probe/tunnel tests). Ruff lint, Ruff formatting, and `git diff --check`
passed. No live inference was used for these checks.

## Recommendation and limits

For the next separately authorized live check, rerun the same fixed six cases
serially, retaining the 12-request ceiling, 120-second timeout, no retries,
and existing resource guards. Compare assessment JSON acceptance and token
usage by stage before considering the full 24-case benchmark. The compact
prompt is an untested prompt change; offline mocks establish schema and safety
behavior, not improved Qwen compliance. Do not interpret citations as semantic
support, and do not change gold labels or validators based on this pilot.
