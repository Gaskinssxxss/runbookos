## M3 adapter and evidence contract

The test-only adapter in `tests/ai_m3_benchmark_v070.py` consumes each case only through the existing `model_facing_input()` projection. It recursively rejects gold-only field names before provider calls. The gold object remains in the separately loaded evaluator dataset and is passed only to `evaluate()` after prediction generation.

For each case, the adapter makes two serial provider calls:

1. Diagnostic selection, validated against the existing four-ID M3 catalog. Unsupported or duplicate IDs are retained as sanitized failure metadata; they do not cause action execution.
2. A `ModelAssessmentReply`, restored from short evidence aliases, sanitized, converted to the existing `StructuredAssessment` schema, and checked by `validate_assessment()`.

The 24-case maximum is therefore **48 provider requests** (24 × 2); the hard budget rejects request 49. Malformed selection, unsupported IDs, provider errors, invalid assessments, and valid abstention have distinct artifact statuses. A failed or interrupted request is not retried. The adapter never creates a RunbookEngine, constructs an SSHAdapter, or dispatches a diagnostic action.

The fixture already supplies observations, so the adapter passes those exact synthetic values as pre-provided context rather than inventing a run. M1/M2 observation objects use a namespaced `m3-fixture-context:<case_id>` provenance identifier, preserve the fixture reference and diagnostic-to-registered-action mapping, and set execution, assertion, and verification states to `unknown`. This identifier is explicitly **not** a RunbookOS execution ID and no claim is made that a command ran. The M1/M2 validator still enforces schema, evidence-reference integrity, advisory-only recommendations, and the rule that unverified fixture data cannot support a `supported` classification.

Predictions are serialized separately from gold labels, contain only structured assessments, selected IDs, sanitized status/error categories, per-case request counts and latencies, and model/runtime identities. The prediction JSON and SHA-256 sidecar are created exclusively with mode `0600`; output directories must be owner-controlled with no group/other permissions. Evaluation reloads and verifies the prediction artifact before projecting it to the existing `EvaluationInput` contract. Evaluation JSON and Markdown are separate artifacts. No prompts, raw provider responses, API keys, or secrets are saved.
