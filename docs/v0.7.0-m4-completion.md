# RunbookOS v0.7.0 M4 — Read-Only Incident Assessment Review

## Scope and architecture

M4 extends the existing `runbookos incidents show` command and authenticated dashboard incident detail. It reuses `IncidentStore.show`, the existing `investigations` rows and `incident_investigations` links, M1/M2 `StructuredAssessment`, and the existing audit chain. No schema migration or second incident API was added. The projection is a pure function; the new store lookup reads one investigation and checks its persisted result hash against the matching `investigation.completed` audit payload.

The dashboard presents every linked investigation separately in its stored link order and labels the last one as the latest linked investigation. The CLI adds `investigation_assessments`, `latest_investigation_assessment`, and `assessment_review_audit` fields to the existing JSON detail response. Neither review path invokes investigation, a model provider, planner, approval, dispatcher, SSH, or remediation code.

## Projection and evidence semantics

`project_investigation_assessment` emits projection version 1. It verifies that the investigation is linked, its result is covered by an `investigation.completed` hash, its incident summary digest matches, assessment schema/catalog versions are supported, assessment incident/investigation IDs match, and persisted observations exactly match observations deterministically reconstructed from the stored diagnostic evidence.

The projection distinguishes direct observations from model inferences and hypotheses. For each observation it carries evidence reference, diagnostic/action, execution and step IDs, time, execution status, assertion outcome, verification state, and recorded result. Redaction is applied to observed result values. Failed assertions remain `failed` and their evidence remains `not_verified`; no projection path promotes evidence.

Model confidence is labeled “model-reported; uncalibrated.” Semantic support remains `unverified`. Per-incident evaluation is `NOT MEASURED` because no validated, explicitly linked evaluation artifact exists. No aggregate M3 benchmark metric is presented as incident-specific performance. Recommendations are escaped plain text, labeled advisory and non-executable.

Missing legacy assessments are shown as `legacy_unavailable`. Unsupported versions, malformed assessments, cross-incident identity/digest mismatches, missing links, and audit-integrity failures produce safe unavailable states with reason codes; malformed stored claims are not rendered.

## Security and compatibility

- The dashboard continues to require the existing authenticated session for incident detail; unauthenticated requests redirect to login.
- All alert, observation, inference, hypothesis, classification, and recommendation text is HTML-escaped. Evidence result data is redacted and bounded in HTML.
- Assessment details are emitted only for investigations linked to the requested incident and validated against that incident identity and digest.
- A failed global audit-chain verification suppresses assessment projection in both CLI and dashboard; individual investigation result hashes are also checked.
- GET handlers perform reads only. The synthetic integration test confirms no execution or approval records are created and the audit event count is unchanged by review.
- Incident lifecycle controls and remediation review remain as before. The assessment view adds no controls.
- Persistence remains additive within the existing `result_json`; no database migration was required.

## Offline demonstration

`tests/test_assessment_review.py` builds a temporary SQLite database, ingests a synthetic alert, stores an M1/M2-shaped assessment and failed diagnostic observation, and associates the investigation using the existing incident linkage API. It then compares the CLI projection with an authenticated loopback dashboard view. It also verifies a legacy investigation, multiple separate investigations and historical ordering, cross-incident rejection, unsupported/malformed assessment states, HTML escaping, failed assertion preservation, audit-chain validity, SQLite integrity, foreign keys, and the absence of execution/approval records.

All data and credentials used by the demonstration are synthetic and created under pytest's temporary directory. No operational or historical database is opened.
