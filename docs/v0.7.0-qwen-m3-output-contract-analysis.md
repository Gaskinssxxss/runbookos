# RunbookOS v0.7.0 — Qwen M3 Output Contract Analysis

## Verdict

**Offline reliability fix ready for review.** The first live run's broad failure categories are confirmed, but the exact historical parse/schema causes are not recoverable because raw responses and field-level traces were intentionally not retained. No further live inference was run for this work.

## Historical failure evidence and limits

The preserved sanitized submission records 24 cases and 30 provider calls:

- 18 cases ended at selection with `invalid_json` / `invalid_model_output` after one request.
- 6 cases had catalog-valid selections, then ended at assessment with `invalid_assessment` / `invalid_model_output` after a second request.
- No case produced an accepted `StructuredAssessment`.
- The six recorded selections were valid catalog IDs; three insufficient-evidence cases selected all four catalog IDs, but that is not an over-limit response because four was the stated limit.

The artifact contains selected IDs, status/category, request counts, latency, and evaluator summaries, but no response text, parse error, Pydantic locations, finish reason, or response sizes. Therefore these historical subcategories cannot be determined:

- Whether selection responses were Markdown fenced, had surrounding text, malformed or incomplete JSON, or valid JSON with an incorrect shape.
- Whether assessment responses had missing/extra fields, invalid nested shapes/classifications/confidence, forged evidence aliases, unsupported verified claims, status conflicts, or advisory-text violations.
- Whether a model response was truncated. The provider's `ModelReply` does not expose finish reason.

The old adapter mapped multiple exception paths to `invalid_model_output`; do not infer a more specific historical cause from that label. The prior five-case v0.6.0 result used a different prompt/contract and does not establish M3 compatibility.

## Contract comparison

| Area | v0.6.0 successful acceptance path | Original M3 path | Finding |
|---|---|---|---|
| Messages | System and user messages; incident text explicitly untrusted. | System and user messages; `model_facing_input()` projection. | Same basic API shape; M3 correctly uses the gold-free projection. |
| Selection prompt | Explicit exact catalog IDs, distinct IDs, configured maximum, empty list when none is justified, no invented evidence/actions, JSON only. | Asked for a minimal set, exact catalog IDs, “at most four,” and JSON, but did not explicitly prohibit duplicate IDs or define empty-list abstention. | M3 prompt was less explicit. |
| Limit enforcement | `_parse_selection` deterministically checked duplicates, limit, and catalog membership. | Pydantic `DiagnosticSelection` allowed up to eight; M3 checked duplicates and membership but did not enforce the prompt's four-ID maximum. | Confirmed M3 implementation gap; fixed offline. |
| Assessment instructions | Detailed category/status/evidence-reference rules, supported-only-if-verified, abstention and advisory requirements, plus a top-level example. | Named required top-level keys and stated that evidence was unverified, but did not specify nested object shapes or exact-output formatting. | M3 contract was under-specified relative to its strict M2 validator. This is a plausible compatibility contributor, not a proven historical cause. |
| Evidence | Actual runbook evidence and issued aliases were validated by the investigator. | Pre-provided fixture observations are wrapped as `unknown` execution/assertion/verification; model receives `E##` aliases and cannot create observations. | M3 correctly avoids claiming executed evidence; this remains unchanged. |
| Provider parameters | 700 output tokens, temperature 0; same local 12,288 context runtime. | 700 output tokens, temperature 0; same runtime. | No confirmed parameter difference explains the failure. |
| Parsing | Production JSON parser with schema validation. | M3 called the same parser, which may close missing final JSON containers. | M3 accepted an implicit repair path; now strict M3 parsing rejects incomplete responses without repair. |

M3 does not use llama.cpp JSON-constrained response mode. The existing OpenAI-compatible provider does not expose a `response_format` contract, and compatibility of that mode with this installed runtime was not established offline. No such request option was added.

## Changes made

Only test/benchmark tooling changed:

1. `tests/ai_m3_benchmark_v070.py`
   - Added explicit JSON-only selection and assessment contracts, with required fields and nested assessment shapes.
   - Enforced the four-diagnostic maximum deterministically. Over-selection is rejected before the assessment request; IDs are never silently truncated.
   - Added strict single-object JSON parsing for this adapter. It does not close delimiters, unwrap code fences, or extract JSON from surrounding text.
   - Requires the exact top-level key sets for both stages and a non-null assessment status.
   - Retains the existing Pydantic models, evidence alias restoration, `validate_assessment`, confidence checks, and advisory-text validation.
   - Persists sanitized stage traces: response byte/character counts, JSON/schema parse states, catalog/evidence validation states, safe validator locations/types, provider token counts, stage latency, and finish reason only if exposed and allowlisted.
   - Does not retain prompts, response text, exception messages, rationale, or arbitrary unsupported IDs. Unsupported IDs are represented by fixed sentinels so the existing evaluator can count them without storing model-provided strings.
   - Marks action-policy validation as `not_applicable_no_actions_executed`; the benchmark adapter does not dispatch diagnostics or evaluate a target policy.
   - Provider failures are classified using exception types only. Provider messages are not saved.
2. `tests/test_ai_m3_benchmark_v070.py`
   - Added coverage for fenced/surrounded/malformed/incomplete JSON, schema errors, response size limits, four-ID boundary and over-selection, duplicate/unknown IDs, missing assessment fields, unsupported classification, forged evidence alias, invalid abstention combination, non-finite confidence, sanitized token/size traces, and prompt gold isolation.
   - Existing regressions continue to cover valid empty-selection abstention, valid structured assessments, unsupported verified claims, timeout/no retry, resource abort, request budget, fake executor isolation, artifact integrity, and evaluator consumption.
3. `docs/v0.7.0-qwen-m3-output-contract-analysis.md` — this analysis.

No production RunbookOS source, assessment validator, evaluator gold data, historical report, approval manifest, model, runtime, or infrastructure was changed.

## Failure trace semantics

New outcomes distinguish `markdown_code_fence`, `unexpected_surrounding_text`, `malformed_json`, `truncated_or_incomplete_json_suspected`, `schema_invalid`, `response_too_large`, `selection_limit_exceeded`, `duplicate_diagnostic_ids`, `unsupported_catalog_ids`, `evidence_reference_rejected`, and `unsupported_verified_claim`. These categories apply to future runs only; they do not rewrite historical results.

`truncated_or_incomplete_json_suspected` is intentionally qualified: without a provider finish reason, an incomplete-looking JSON parse cannot prove token truncation. `finish_reason` is null when unavailable. Validation trace locations contain only known schema field names, numeric indexes, or a generic unrecognized-field marker. Token counts are retained only for known token-usage keys and bounded nonnegative integers.

## Security invariants preserved

- No SSH adapter, engine, executor, or mutable action is imported or invoked by the benchmark adapter.
- Fixture evidence remains synthetic and `unknown` for execution, assertion, and verification.
- Model-facing input still comes only from M3's `model_facing_input()`; gold labels and annotation rationales remain excluded.
- Catalog membership, selection maximum, evidence alias existence, M2 assessment validation, finite confidence, unverified-evidence rules, and advisory-only recommendation validation fail closed.
- Malformed JSON is rejected; it is not converted to abstention. No automatic retry was introduced.
- No raw response text or provider exception message is written to artifacts.
- Historical prediction artifacts and reports remain unchanged.

## Remaining limitations

- The actual historical model responses cannot be classified more precisely without the raw content, which was deliberately not retained.
- The structured response schema remains demanding for the current model/runtime; the prompt correction does not prove Qwen will comply.
- The generic provider does not expose response finish reason, so truncation evidence and token-budget exhaustion cannot always be distinguished.
- M2's deterministic validator verifies structure and evidence-reference integrity, not semantic truth.
- No new live inference has validated these prompt and trace changes.
